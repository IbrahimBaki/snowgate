# YallaFlow Agent Contract

YallaFlow is the engineering governance layer for this repository: durable project memory, adaptive workflows, and evidence-backed delivery. It applies Adaptive Spec-Driven Development where the work needs it — specification depth must match the work type and scope. The Agent orchestrates; YallaFlow governs; project memory persists. Developers work with Git; agents work with YallaFlow: the complexity stays inside YallaFlow, not in the developer's prompt.

## Core rules

1. Discover before asking. Technical unknowns belong in repository discovery; ask only about material business ambiguity or unavailable information.
2. Understand before changing. Route the request to the correct workflow and establish the required evidence/spec first.
3. Prove before claiming. No work item may become DONE without fresh verification evidence.
4. Remember after finishing. Promote only durable knowledge into context/ or decisions/; keep execution noise with the work item.
5. Revalidate before trusting stale knowledge. Project context whose supporting evidence changed since it was verified may be stale; revalidate it before relying on it.
6. Investigation is read-only unless the work item is explicitly converted to an implementation workflow.
7. Record material deviations or assumptions as rulings in the work item progress ledger.

## Start sequence

Orient automatically. At the start of every session in a repository that contains .yallaflow/, before handling the first request, run yallaflow brief yourself — the developer does not need to say "use YallaFlow" (saying it explicitly still works). Then process the developer's request against what the brief reports: whether project understanding is established, whether this is a Shared Project, the current project memory, and whether this YallaFlow is compatible with the project (if brief reports an incompatible version, stop before any YallaFlow state change and tell the developer which version the project requires).

In a fresh session, run yallaflow brief first: one read-only orientation (agent contract state, active and most recent work, project memory, sources, pending legacy reconciliation) that names the next command to run. It is project-first: it shows what project memory says about the project, bounded per area, before YallaFlow status, and for a brownfield repository without project memory it names the onboarding step (see the Brownfield onboarding sequence). It does not replace yallaflow resume/handoff/guide; it tells you which one applies. For a brownfield project with an approved baseline (.yallaflow/PROJECT.md and context/ populated by `yallaflow baseline approve`), read PROJECT.md and only the context docs relevant to the current request first; do not blindly rescan the whole repository for every request — but repository evidence remains authoritative when durable context is stale (see the project memory sequence). Otherwise read .yallaflow/config.yaml, .yallaflow/PROJECT.md, .yallaflow/state/current.yaml (.yallaflow/local/state/current.yaml in a Shared Project), then load only the context relevant to the current work item.

## Project understanding sequence

Every YallaFlow project establishes durable project understanding before substantial work; only the evidence differs. For an existing (Brownfield) repository without approved project understanding, brief, start, route, and guide report PROJECT_UNDERSTANDING_REQUIRED. When the developer asks for real work in that state ("Fix invoice totals"), do not wait to be asked to "understand the project": establish the understanding first through the Brownfield onboarding sequence (one deep, evidence-backed baseline that a human approves), then continue with the requested work after that review boundary. YallaFlow enforces this boundary: in a Brownfield project without approved project understanding — including while a baseline draft awaits the developer's approval — no normal engineering work item (feature, bug, investigation, change, refactor, release, or an unclassified yallaflow start intake) can be created or routed: start, the direct commands, file intake, and route refuse with PROJECT_UNDERSTANDING_REQUIRED, create nothing, and name the baseline as the NEXT VALID ACTION; and no work item can enter or continue an application-writing stage. A read-only question about the project ("How does subscription renewal work?") is engineering work too: understand deeply once, then revalidate precisely. Do not ask the developer to run anything: start the baseline yourself with the developer's original request as its objective (yallaflow baseline start --objective "<the request>"), so the request survives the baseline — the baseline stays project-wide and the request only deepens the relevant areas. Ask only for the human baseline approval. After the developer explicitly approves, record it and continue the original request automatically (yallaflow baseline approve and yallaflow brief name it; start it with yallaflow start "<the request>"): never ask the developer to repeat it, and never run another repository-wide discovery for it. Greenfield projects are never gated.

Not every request is engineering work. Transient operational assistance — start Docker or a dev server, open the application, show logs, check git status, inspect local processes or ports — is handled directly, without a YallaFlow work item and without waiting for project understanding: it changes no application code and no project memory, and its observations are transient runtime state, never durable facts. Project-semantic engineering work — understanding, changing, fixing, investigating, refactoring, or releasing the project's behavior — goes through YallaFlow. You interpret which one a request is; when operational help turns into a question about how the project behaves ("why does the renewal job fail?") or a change, it is engineering work, and YallaFlow's deterministic boundary applies. Once project understanding is approved, never repeat a repository-wide scan: later work reads the approved memory and rediscovers only what freshness or the objective requires. One expensive, useful bootstrap plus small targeted rediscovery later — not repeated full rescans. For a Greenfield project, never scan an empty repository: understanding comes from the product intent, supplied requirements and sources, and decisions as they are approved, recorded through ordinary work and knowledge.

## Purpose-aware discovery sequence

Discovery is better when you know what the understanding is for. There are three discovery modes: bootstrap discovery (wide initial understanding: repository → approved durable memory), intent discovery (existing memory + a new objective → a targeted deep dive), and freshness discovery (supporting evidence changed → targeted revalidation → reconfirm, supersede, or dispute). A first baseline always covers the canonical core (purpose, architecture, applications/modules, backend and frontend stacks, database/storage, authentication, authorization/roles, business workflows and rules, external integrations, routes/APIs, environments/configuration, testing, CI/CD/deployment, conventions, shared components, operational/security risks, unresolved knowledge, discovery limitations) — durable understanding, not trivia. When the developer states a future objective ("we will redesign the whole UI while preserving business behavior"), record it as a discovery lens with yallaflow baseline start --objective "..." --preserve "..." [--focus "..."] (or yallaflow purpose set <work-id> --objective ... for intent discovery on other work) and go deeper where it points — you reason about which areas matter; YallaFlow only persists the structured contract. Purpose and preservation intent are work intent, stored in work/<id>/purpose.yaml: never promote them as project facts and never write planned future work into project memory; delivery convergence may use preservation intent as an input.

## Routing sequence

For an unclassified request, create an intake with yallaflow start, classify it using the allowed work_type, scope, and confidence values, explain the reason, then apply the decision with yallaflow route. The CLI validates and persists the decision; it does not perform semantic inference. Scope classification is not just about code size: consider financial/accounting invariants, security/privacy impact, authorization changes, persistent data-model/migration changes, cross-module derived state, external integration contracts, public APIs, irreversible behavior, and concurrency/transaction rules. A small UI change can stay bounded; a small-looking change touching system-wide financial correctness may warrant architectural depth and its specification/planning review gates. YallaFlow validates the allowed values only — it never classifies semantically itself.

Direct classified commands are shortcuts only for work whose type and scope are already known: yallaflow feature|bug|investigate|change|refactor|release "<title>" --scope <spike|bounded|architectural>. --scope is required; never guess or default a scope to make a direct command succeed. If the type or scope is not already known, use yallaflow start and classify with yallaflow route instead. If YallaFlow rejects a type/scope combination (for example feature with spike), do not force or work around it — choose a supported classification (e.g. investigation, or bug with spike, for exploratory work) or route through yallaflow start.

## Behavior contract sequence

Skills define engineering behavior. Work items pin the behavior they were created with. Before engineering work, run yallaflow guide for the work item. Follow the pinned skill order and retrieve exact package-owned instructions with yallaflow skill <skill-id> --work <work-id> (by default the active work item's pin): a work item always gets the exact, immutable instruction version its Behavior Contract pinned, even after YallaFlow is upgraded. Record completed work explicitly with yallaflow checkpoint; never infer completion from conversation. Workflow stages remain authoritative; do not modify application code when guidance reports that modification is not authorized. Once a required review gate is approved, continue automatically to the next configured boundary or blocker — do not ask again for permission that was already given (e.g. after "approve and execute", proceed to the next ready step without a redundant confirmation prompt).

## Brownfield onboarding sequence

For an existing repository with no durable project context yet (yallaflow brief says so), onboard it through the Brownfield baseline — there is no separate onboarding workflow. yallaflow inspect gives a bounded, read-only repository inventory: manifests with deterministic framework hints, recognized source files, documentation candidates, container/CI configuration, and the Brownfield/Greenfield classification with its reasons; it writes nothing and never reads documents. Then run yallaflow baseline start, perform repository/runtime discovery following yallaflow skill repository-baseline, complete the repository-baseline checkpoint, and record findings with yallaflow baseline draft <work-id> --file <baseline.json> — every fact needs a status (confirmed/inferred/unresolved), evidence, and source (repository/runtime/user-confirmed); prior chat/model memory is never evidence. Things the discovery could not inspect go in the draft's limitations array, not in facts. Declare what the discovery actually read in the draft's coverage (inspected: read directly; sampled: inspected selectively): a long list of facts never implies that the whole repository was read, and you never claim completeness without evidence. yallaflow baseline show presents inspected, sampled, not inspected, unavailable, and unresolved coverage for the developer's review.

"Do not change application code" and "read-only / do not write anything" are different instructions. When the user asks you to understand, orient to, or onboard a brownfield project and says not to change application code, the onboarding YallaFlow workspace writes are authorized and need no further permission: yallaflow baseline start, registering material documents with yallaflow intake add, completing the repository-baseline checkpoint, and yallaflow baseline draft. They change only .yallaflow, never application code. When the user explicitly asks for a completely read-only or no-write operation, do not mutate .yallaflow either: use only read-only commands (yallaflow inspect, brief, status, context status, baseline status/show) and report what onboarding would record.

Material documentation: review the documentation candidates yallaflow inspect lists and read the ones material to understanding the project. For a PDF, DOCX, XLSX, or PPTX you cannot read directly, register it with yallaflow intake add <baseline-work-id> <path> and read its extracted text with yallaflow source show SRC-#### --content instead of guessing; preserve-only formats have no extracted text. Cite a document inside the repository as repository evidence (its path). A document is evidence of what the document says, not proof of what the code does — confirm against code or runtime where you can. Record material documents you did not read as not-inspected limitations.

Baseline facts describe durable project truth: declared configuration, code structure, conventions, evidenced business rules. Transient runtime state (which containers are running, open ports, the current branch, process lists, session tokens, machine-specific absolute paths) is never a durable fact; record the durable configuration that declares it, and keep a transient observation in work notes or a limitation.

Present the draft to the developer in plain language — what you established, what stays unresolved, what you could not inspect — and ask them to review it (yallaflow baseline show prints the full record). Approval is the developer's decision, never yours: only when they explicitly approve it in the conversation (for example they reply "Approve") record it with yallaflow baseline approve <work-id> --note "Approved by <who> in the agent session: <their words>", then continue the original request. If they ask for changes, record yallaflow baseline feedback <work-id> --changes-requested --note "..." and revise the draft. Never infer approval from silence, a general "ok", or an instruction to get on with other work, and never treat an unapproved draft as project memory. Only an approved baseline updates durable project memory (context/index.yaml and its PROJECT.md/context/ projection). The baseline is the initial foundation; normal work keeps project memory current — there is no baseline refresh.

## Project memory sequence

Work records preserve history. Project memory preserves current understanding. The canonical project memory is .yallaflow/context/index.yaml (CTX-#### facts, each current, superseded, or disputed, with confidence, provenance, evidence, and a verification point); PROJECT.md and context/*.md are its projection and show current knowledge only.

Before work: read the relevant current context; check freshness with yallaflow context status (or yallaflow context affected) for the areas the work touches; rediscover only where supporting evidence changed (MAY_BE_STALE / STALE_EVIDENCE), a fact is DISPUTED, or knowledge is unresolved. MAY_BE_STALE does not mean false. Freshness is mechanical: repository file evidence is checked by SHA-256 content hash, which works without Git (a recorded Git commit is only a fallback, e.g. for directory evidence); UNKNOWN means there is no verification point (runtime or user evidence, or directory evidence without Git) and does not mean stale. yallaflow brief lists NEEDS CARE: facts that are unresolved, disputed, MAY_BE_STALE, or STALE_EVIDENCE — knowledge whose state or freshness is mechanically known to need care. It is not a risk list: confirmed, fresh facts about security, architecture, or technical debt are ordinary project knowledge you interpret yourself.

During work: do not silently trust stale context, and do not rescan unrelated areas that fresh durable context already covers. Record what you could not inspect (no production access, not sampled, out of scope) with yallaflow limitation add — a discovery limitation is work-scoped and is never a project fact.

After work: propose durable knowledge and explicitly relate it to existing facts when it reconfirms (--reconfirms CTX-####: still true, fresh evidence), supersedes (--supersedes CTX-####: no longer true; the old fact becomes history), or disputes (--disputes CTX-####: conflicting evidence you cannot settle) them. YallaFlow validates the referenced fact and the transition; it never infers semantic equivalence or truth. Never rewrite historical work to reflect newly discovered truth.

## Delivery intent and convergence sequence

Passing tests does not prove that the delivered implementation matches the approved intent. Verification asks whether the recorded technical checks pass; code review asks whether the implementation is technically acceptable; convergence asks whether the delivered implementation satisfies the approved requirements and acceptance criteria. When yallaflow guide shows a delivery-convergence contract (feature work, architectural changes): before completing the intent checkpoint (specification when the work has one, otherwise requirement-clarification), extract the approved intent as stable requirements (REQ-###) and acceptance criteria (AC-###) and record them with yallaflow requirement record <work-id> --file <requirements.json>, each with provenance (request, a specification section, a linked SRC-#### source, or an answered Q-###). Keep them proportional — a bounded feature may need one requirement — and never invent intent the user did not express; the approved specification stays authoritative. After verification, inspect the implementation against every active criterion and record one finding each — satisfied, partial, missing, or contradicts — with a reason and evidence (repository paths, verification:V-###, runtime:/user: observations, or a child's convergence:PF-####/CV-###) using yallaflow convergence record <work-id> --file <convergence.json>; record implemented behavior no criterion requested as unrequested and resolve it as accepted (with a reason) or removed. Findings are yours to judge; YallaFlow validates and records them and never converts one. A finding goes stale when the work is reopened or revised, its criterion changes, or cited evidence changes — re-assess instead of arguing with it. DONE requires every active criterion to be currently satisfied. If approved intent changes after it was fixed — a new source attached, or requirements changed — YallaFlow raises a pending impact: run yallaflow impact status <work-id>, decide for every completed stage whether the change affects it (with a reason), and record it with yallaflow impact assess <work-id> --file <impact.json>. YallaFlow revises the affected stages through the audited checkpoint-revision path and deletes no evidence. Requirement identity, convergence, and impact are work-delivery records, not project facts: only stable knowledge learned from the work goes through the knowledge sequence.

## Legacy context reconciliation sequence

Legacy (v0.3.5 append-only) project knowledge is not canonical current truth until it is reconciled; migration is not reconciliation. Use yallaflow context reconcile start (never a blind yallaflow context adopt), inspect candidates with yallaflow context reconcile show, and declare one explicit relationship per RC-#### candidate — new, merge-with, reconfirms, supersedes, disputes, skip (with a reason), or limitation — with yallaflow context reconcile plan --file <decisions.json>, following yallaflow skill context-reconciliation. merge-with collapses two or more legacy candidates that are the same statement into one canonical fact (its target is another RC-#### candidate); reconfirms records one more historical observation of a truth already represented (an existing CTX-#### fact or another candidate's fact, of the same kind of knowledge). Relate a candidate to an existing CTX fact with reconfirms, supersedes, or disputes, never merge-with. Base every relationship on evidence and reasoning, never on wording similarity alone; do not semantically merge facts you have not examined. When you cannot safely decide whether items are duplicates, separate facts, a supersession, or a contradiction, leave the candidate undecided and record a question (yallaflow question add <reconciliation-work-id>) for human review — never guess. Preview the resulting memory with yallaflow context reconcile preview; a human approves with yallaflow context reconcile approve; only then yallaflow context reconcile apply. Never approve on the human's behalf, and never rewrite historical work (baseline.yaml, knowledge.yaml, earlier work.md) to make a migration cleaner: work history is immutable, reconciliation interprets it, project memory evolves.

## Shared Project sequence

A Shared Project (config.yaml shared.enabled, set once by a maintainer with yallaflow shared enable) is shared through ordinary Git: project memory, work, sources, and decisions are committed; personal runtime state (.yallaflow/local/: this checkout's identity and active work) is never shared. Team members need no join command. Work and source IDs there are branch-safe (PF-<tag>-####, SRC-<tag>-####); legacy PF-####/SRC-#### IDs stay valid. Every work item records the project-memory state it started from (work/<id>/memory.yaml). Work against the shared memory, but on a feature branch never write canonical memory: yallaflow knowledge promote stages a reviewed context candidate as the work's memory delta, and canonical integration happens only on the integration branch (yallaflow shared integrate — applied automatically when you promote on the integration branch). A staged delta is a completed knowledge disposition: DONE does not wait for integration. Never overwrite shared canonical knowledge silently: if a fact your candidate relates to changed in parallel (yallaflow finish, shared status, or shared check reports it), revalidate against the current fact — reject the stale candidate with a reason and propose again against the current CTX fact — or record a question when the conflict is a real business decision. Exact duplicates are merged mechanically; semantic duplicates are yours to judge. Baseline approval and legacy reconciliation are canonical writes: run them on the integration branch. If the installed YallaFlow is older than the project requires, stop before any state change.

YallaFlow and you never commit, push, pull, rebase, merge, or force-update branches on your own initiative; the developer stays in control of source control. Suggest an ordinary Git action only when it is necessary (for example, "update your branch with main, then ask me to continue").

## Finish protocol and developer language

You own the completion protocol, not the developer. Before telling the developer a task is ready: verify the work, run delivery convergence when the contract requires it, complete the knowledge review, then run yallaflow finish <work-id>. It checks the lifecycle, project integrity, and — in a Shared Project — whether shared memory changed under the work's memory delta. Relay its developer lines ("Implemented and verified. The project knowledge is up to date. Ready to push."); act on its agent lines yourself. Keep normal-path output in outcome language: do not narrate PF/CTX/K identifiers, checkpoints, freshness states, or promotion mechanics unless they help a diagnosis or the developer asks — yallaflow finish --verbose, status, and the work records keep the full audit. Ask the developer only for real business decisions, human review gates (such as baseline approval), or exceptional source-control actions.

## YallaFlow state ownership

Never edit YallaFlow-owned structured or history state directly when a supported command exists — run the command. CLI-owned: work/<id>/meta.yaml, progress.yaml, progress.md, knowledge.yaml, reviews.yaml, questions.yaml, baseline.yaml, discovery.yaml, decomposition.yaml, reconciliation.yaml, legacy-context.md (retired legacy sections), requirements.yaml, convergence.yaml, impact.yaml, evidence/ (verification ledger), memory.yaml (Shared Project memory base, staged delta, integration record), purpose.yaml (discovery purpose and preservation intent), context/index.yaml, sources/ (originals and metadata), state/current.yaml (or local/state/current.yaml and local/identity.yaml in a Shared Project — personal, never committed), and decisions/ ADRs YallaFlow generated. Generated projections (the managed blocks in PROJECT.md, context/*.md, and AGENT.md, and the YallaFlow bootstrap block in a repository-root AGENTS.md or CLAUDE.md) are regenerated with yallaflow context render / yallaflow agent refresh, never hand-edited. work.md is shared: you write its narrative sections (discovery notes, specification, plan, findings, result), but its CLI-appended lifecycle records (Routing Decision, Source Added, Request Revised) are history — never edit them. If a state file looks wrong, run yallaflow doctor and fix it through commands, not by editing.

## Sources, evidence, and generated artifacts

Never copy a secret value into YallaFlow state. Credentials, passwords, API keys, access tokens, Authorization/Bearer values, private keys, cookies and session secrets, and connection strings with embedded credentials stay where they are: cite the file (.env is valid evidence) and name the setting ("DB_PASSWORD is read from .env"), never its value — in facts, evidence, notes, summaries, limitations, knowledge candidates, rulings, or requests. YallaFlow redacts recognizable secret values (KEY=<redacted>) before anything is persisted, without changing developer files or preserved source originals; that is a safety net, not permission.

Material user-provided artifacts must not exist only in conversation memory. A source is an original user/project input (screenshot, PDF, DOCX, spreadsheet, requirement file) and lives, immutable, under .yallaflow/sources/SRC-####; evidence is proof produced during engineering or verification (work/<id>/evidence/, verification runs); a generated artifact is an optional output of the work itself. When a user-provided artifact materially affects a work request and you can access its file path, register the original with yallaflow intake add <work-id> <file> (or yallaflow intake <file> for new work) so it is linked to the work item; for DONE work add --reason, which records it as a recovered source added after completion (never as if it existed during execution). If you cannot access its bytes or path (e.g. an image pasted into chat), do not claim it was preserved: record yallaflow limitation add <work-id> --type uncaptured-artifact --area requirement --summary "<what the artifact showed>" --reason "<why it could not be captured>", and describe what it showed in the work item. Not every request needs a file — only artifacts that materially shape the requirement. Never register verification output as a source, and never edit a preserved source; capture a new version instead.

## Knowledge sequence

Work progress is not project knowledge, and a local ruling is not automatically an ADR. Near completion, propose only stable future-facing knowledge with yallaflow knowledge propose, citing evidence as existing repository paths (optionally path#symbol or path:12-40), runtime:<observation>, verification:V-###, or user:<confirmation>. Promote or reject every candidate, or explicitly record yallaflow knowledge review --none. Never promote execution noise or infer durable knowledge with keyword matching.

## Verification

Prefer argv verification: yallaflow verify <work-id> -- <executable> [args...]. Use --shell "<command>" only when shell operators (pipes, redirection, &&) are actually needed. Failed attempts remain in the append-only evidence ledger; re-run correctly rather than hiding them.

## Handoff and completion language

Conversation context is disposable; project state is durable. At a safe boundary — or when the session itself is getting large — checkpoint progress, leave the working tree intact, and run yallaflow handoff before continuing in a fresh session; it surfaces the PRIMARY UNRESOLVED OBJECTIVE when one exists (from a reopen reason, a checkpoint revision reason, or an active blocker) so a new session does not have to infer it from lifecycle history alone. Only say a project is complete when the parent/project work item itself is DONE; a child reaching DONE is child-level completion (e.g. "PF-0006 DONE, 5/7 required children complete"), never "project complete". YallaFlow never commits automatically and never requires a clean Git tree for DONE, but a dirty tree at a DONE boundary is worth a source-control checkpoint before unrelated work begins.
